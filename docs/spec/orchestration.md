# 生命周期规格

## 单模块生命周期

每个模块内部负责：检查 → 计划 → 执行 → 验证 → 记录。

主动移除负责：读取记录 → 检查当前状态和所有权 → 计划 → 执行反操作 → 验证 → 更新记录。

这些是职责，不是要求所有项目具有完全相同的脚本。

## 完整安装/应用流程

```text
读取平台和 Profile 配置
    ↓
校验配置引用、依赖、能力和平台条件
    ↓
生成正向执行计划
    ↓
按计划调用公开操作
    ├── packages.<package>.install(context)
    ├── environment.(attach|get|set)(context)  # 一次处理环境变量集合
    └── configurations.<config>.apply(context)
    ↓
记录实际执行结果
    ↓
整体验证与结果汇总
```

Profile 是由 Bootstrap 读取的用户编排配置，采用 TypeScript 表达，以获得模块对象、操作和配置参数的静态类型约束。运行时仍需执行必要的对象引用、能力和平台条件校验。

每个平台独立声明一套完整 Profile，不要求存在跨平台 base profile 或继承覆盖关系。

Profile 描述 Packages 和 Configurations 阶段中的对象集合及其阶段内顺序，并选择 Environment 阶段需要发布的变量集合：

```text
packages
  → environment
  → configurations
```

它还描述传入的用户配置参数以及失败和反操作策略。Environment 阶段本身只有一个整体计划项，不按变量拆分顺序。Profile 中引用的对象和参数受到对应模块公开契约的类型约束，不能声明模块不支持的对象、操作或参数。Profile 不描述软件包、环境变量或配置对象的内部实现步骤，也不直接负责平台路径解析或平台判断。

Bootstrap 根据 Profile 生成三段式计划，但不把批量操作下沉给任何模块。每个计划项对应一个模块公开的对象级操作；计划中的上下文包含平台信息、Environment 解析后的语义值、用户选项和状态记录上下文。Bootstrap 负责组装上下文，但不替对象实现内部逻辑。后续 Packages/Configurations 操作以及它们启动的子进程使用该上下文，不依赖 Bootstrap 的父 shell 自动获得新变量。

普通重复部署不执行显式卸载：如果目标已经满足，操作返回 `success.unchanged`，阶段继续。只有用户明确请求重新安装、重新应用或重建时，才先按对应领域规则执行 `uninstall()`、`remove()` 或其他已公开的清理操作；清理成功后才允许重新执行正向操作。

三阶段顺序由 Bootstrap 固定：Packages → Environment → Configurations。Profile 只能决定 Packages 和 Configurations 阶段内部对象的声明顺序，并选择 Environment 阶段的变量集合。阶段顺序保证了配置应用可以使用前两个阶段已经准备好的软件和环境；若未来需要跨阶段反向依赖，应扩展阶段模型，而不是绕过固定顺序。

每次运行 Profile 都从 Packages 阶段开始，但不是无条件重复产生副作用。各模块自己检查当前现实状态和自己的记录，决定操作是快速完成还是执行必要动作；Bootstrap 不判断模块是否应跳过。Packages、Environment 和 Configurations 的完成状态彼此独立，前一阶段已完成不因后一阶段失败而失效。

- 各配置的准备、构建、生成、应用和验证都属于对应配置自己的流程。
- 配置自身实现公开操作，只报告自己的领域结果；Configurations 提供工具和运行上下文。
- Packages 和 Environment 同样由各自对象拥有内部实现，Bootstrap 不逐条执行其内部步骤。
- 整体验证由 Bootstrap 组织公开能力和结果，不重新实现模块内部检查。
- 计划校验失败时，必须在产生部署副作用前停止。跨对象执行结果仍由各模块分别定义。

## 严格失败策略

只支持严格模式：必要计划项失败，停止后续正向计划项，并汇总已完成、失败和未执行项。计划项失败不会自动改变其他模块的内部流程。

公开操作只有 `success` 和 `failure` 两种确定结果。Bootstrap 只根据这两个结果决定是否继续：成功继续后续对象或阶段，失败停止后续正向编排。成功结果必须区分本次是否产生变化：

```text
success.changed
success.unchanged
failure
```

`success.changed` 才由 Bootstrap 在当前阶段的取消计划中登记对应公开取消操作；`success.unchanged` 不登记取消项。失败时不登记正向取消项，但模块必须报告失败前产生的副作用、残留和可用补救信息。Bootstrap 不维护跨模块混合计划，而是分别维护 Packages、Environment、Configurations 三个阶段的取消计划。

例如某个项目部署单元的准备步骤失败，不继续该项目部署或后续项目。

停止正向执行不等于自动回退，也不禁止清理。是否调用反操作、作用范围由偏好配置决定；模块执行自己的补救步骤，Bootstrap 不介入内部细节。

## 能力与策略分离

所有产生副作用的公开操作都应有适用的取消操作，或明确说明不可逆限制。取消操作不是正向操作内部自动拥有的反向动作；Bootstrap 根据本次编排记录和策略决定是否调用它。无法完全撤销时说明限制，不承诺系统级事务或无条件恢复。

| 正向能力 | 反向能力 |
| --- | --- |
| 安装软件 | 卸载受管理的软件 |
| 创建符号链接 | 移除链接，不删除源 |
| 部署副本 | 移除受管理副本 |
| 替换已有内容 | 在有备份且安全时恢复原内容 |
| 发布变量 | 恢复旧值或移除新增值 |
| 项目构建/生成 | 调用声明的适用清理能力 |

模块记录原状态、本次动作和所有权，反操作前检查当前状态。无法安全处理或处理失败时报告原因与残留，不能声称已经恢复。

何时调用、调用哪些能力及其默认偏好由后续偏好配置决定，不写死在底层能力中。

## 移除流程

Bootstrap 根据用户配置和各模块的领域记录生成移除或取消计划，实际执行范围由策略选择。正向执行过程中，每个模块以自己的阶段执行作为一个独立完成单元。Bootstrap 只在模块内部记录该模块本次成功且产生变化的对象及其取消操作；模块完成后，其完成状态与后续模块独立。模块内部执行失败时，可以按该模块自己的策略取消本模块本次已完成的对象；Environment 或 Configurations 后续失败，不自动改变已经完成的 Packages 模块。

各模块的取消只针对各自未完成或被明确要求取消的模块，不因为后续模块失败而自动跨模块取消。若用户主动执行完整移除，Bootstrap 才按 `Configurations → Environment → Packages` 的顺序分别启动三个模块的公开取消操作。

```text
读取执行记录和当前实际状态
    ↓
生成反操作计划
    ↓
configurations.<config>.remove(context)
    ↓
Environment.unattach(context)
    ↓
packages.<package>.uninstall(context)
```

例如 Packages 模块本次需要安装 `A → B → C`。只有当 Packages 模块自身完成其全部要求后，Packages 才报告模块完成；若在 B 处失败，Packages 按本模块策略处理已经安装的 A，并报告 Packages 未完成。若 Packages 已经完成，之后 Environment 或 Configurations 失败，不改变 Packages 的完成状态，也不自动卸载 A、B、C。

Environment 是自己的整体完成单元；Configurations 按配置对象执行，但其模块完成和取消范围也只由 Configurations 自己决定。上述规则不代表模块提供跨模块批量操作；Bootstrap 只决定启动哪个模块、何时启动以及是否根据策略请求该模块执行取消。

配置的移除由各配置自己的撤销操作处理；项目 clean 是否属于某个配置流程，由该配置自行定义，不由 Bootstrap 猜测。项目 clean 的范围由项目说明，不等于用户环境的部署移除。

软件卸载检查安装记录与所有权，不能将用户原有软件误判为本项目安装的软件。

## 回退与主动移除

- 模块内取消只针对该模块本次未完成或被明确要求取消的内容；后续模块失败不会自动改变已经完成的模块。
- 主动移除针对已部署内容，按声明、记录与策略分别调用各模块的公开取消操作。
- 两者都需要能力支持，具体恢复程度受外部系统与动作限制。
- 追求像“冰箱贴”一样低侵入、可撤销，但不承诺抹去所有痕迹。
- 运行时缓存等非部署产物暂不纳入清理范围。

模块报告各自领域的结果，并说明残留、限制和可用取消操作；Bootstrap 只提取成功/失败等最小编排信号，成功继续、失败阻塞，不解释模块内部状态，也不强制转换成统一领域状态。需要了解具体原因时，由用户查看对应模块的记录和诊断。
