# 模块能力规格

## 模块关系

系统包含三个相互独立的生命周期模块：

```text
Packages       软件包管理
Environment    环境变量管理
Configurations 配置应用能力与操作
```

三个模块不互相调用，也不介入彼此的内部步骤。Bootstrap 只负责选择模块、决定顺序、传递必要结果、汇总状态和执行整体策略。

## 共同原则

- 每个模块负责自己的检查、计划、执行、验证、记录和取消操作。
- 需要取消时，由对应模块提供适用的公开取消操作；不能完整取消时明确限制。
- 取消操作前检查实际状态和所有权，不能误删用户内容。
- 状态记录不是现实本身；每次操作都检查实际环境。
- 取消操作是否执行及其范围由编排策略决定，不在模块能力中自动跨模块扩展。
- 模块失败时向 Bootstrap 报告足够的编排信号、残留和不确定性。
- 三个模块不强制共享同一个领域结果枚举；每个模块可以定义适合自身的结果模型。
- 对 Bootstrap 暴露的最低共同语义是：操作成功或失败，以及是否产生变化；详细结果、记录和内部状态由模块自行解释和保存。Bootstrap 成功时继续，失败时阻塞。

## Packages：软件包管理

Packages 是一个提供软件包目录和生命周期操作的模块对象。它决定当前项目能够管理哪些软件包，并对外提供对应的对象级操作：

```text
packages.neovim.install()
packages.neovim.uninstall()
```

Packages 不提供 `installAll()`、`uninstallAll()` 之类的整体批量编排操作。多个软件包的选择、顺序、失败策略和逐项调用由 Bootstrap 负责；哪些包存在、每个包如何安装和验证由 Packages 自己拥有。

Packages 可以接收平台能力、平台相关数据和运行上下文。具体如何确保包管理器可用、如何调用包管理器以及如何验证结果，属于 Packages 的内部实现，不作为 Bootstrap 需要介入的步骤。

Packages 内部可以使用平台包管理器完成安装和卸载，并自行检查、验证、记录和处理失败或未完成情况。对外只暴露软件包级操作结果；需要取消或卸载时，外部只调用 Packages 提供的公开能力，具体处理由 Packages 自己解释和执行。

Packages 不负责软件配置、环境变量、配置文件链接、项目构建或整体顺序。包管理器自身的安装/准备属于平台适配能力，但由 Packages 流程统一使用。

## Environment：环境变量管理

Environment 是环境变量契约的权威来源。它决定当前项目有哪些稳定的环境变量、每个变量的语义类型、是否必需以及默认解析规则。

环境变量的发布是一个整体操作，不按变量逐个发布。Environment 对外提供环境集合级生命周期操作：

```text
environment.attach(context)
environment.get(context)
environment.unattach(context)
```

单个变量对象用于定义、引用和读取变量契约，不作为 Bootstrap 逐项调用的生命周期对象。

Environment 负责将当前 Profile 所需的全部环境变量解析为一个集合，并同时完成持久发布和当前流程运行时注入。平台适配层只负责把同一个变量契约解析为当前平台的实际值；不能改变公共变量集合、变量类型或变量语义。Bootstrap/Profile 可以为已定义变量提供经过验证的值覆盖，但不能新增平台私有契约、删除必需变量或改变变量类型和语义。

Environment 内部如何解析变量集合、持久发布、注入当前流程、检查状态、记录原值和执行恢复，不作为 Bootstrap 需要介入的步骤。一次 Environment 操作的结果覆盖本次集合操作；模块内部可以逐变量处理，但这些不是 Bootstrap 的计划项。

Environment.attach() 建立三种可观察范围：

- 当前 Bootstrap 流程及其显式传递该环境的子进程可以使用；
- 持久发布成功后，之后从正确平台入口启动的新进程可以使用；
- 已经运行的外部进程不承诺自动刷新。

启动 Bootstrap 的父 shell 也不能被普通子进程直接修改。若需要当前 shell 立即获得变量，必须通过专门的环境输出/加载入口，由用户使用 eval、source 或平台等价机制主动加载。

Environment 不负责软件安装、配置内容应用、文件链接、项目构建或资源生成。

环境契约原则：

- 各支持平台原则上提供相同的公共变量集合。
- 每个变量拥有稳定、明确的语义类型，例如 DirectoryPath、FilePath、ExecutablePath、Boolean 或 String。
- 同一变量在不同平台只能有不同的实际值和发布方式，不能改变语义。
- 必需变量在当前平台无法解析时必须报告错误，不能静默省略并让消费者自行判断平台。
- 变量名、类型和语义是稳定契约；平台默认值由平台适配层解析，用户定制值由 Bootstrap/Profile 传入并由 Environment 验证。

持久发布不保证刷新已运行程序，也不自动修改启动 Bootstrap 的父 shell；当前流程和显式传递环境的子进程可以立即使用新环境。

## Configurations：配置应用能力与流程出口

Configurations 是一个提供配置对象和应用操作的模块。它决定当前项目能够提供哪些配置，并对外提供对应的对象级操作：

```text
configurations.neovim.apply(context)
configurations.neovim.remove(context)
```

每个配置自行定义内部应用步骤、顺序、判断和验证方式。Configurations 不负责 Profile 选择、配置间排序或整体流程编排；Bootstrap 选择并调用具体配置。配置可以接收环境变量、平台能力和编排者提供的平台差异数据，例如配置目标路径。

Configurations 同时提供配置应用所需的通用工具和运行上下文，例如：

- 解析后的平台路径和语义目标；
- 当前部署流程的环境变量；
- 文件、目录、链接、复制、替换等基础操作；
- 打包或命令执行能力；
- 状态、所有权和备份记录能力；
- 对应的撤销、恢复和清理工具；
- 平台能力和限制报告。

配置项目使用这些能力定义自己的应用流程，Configurations 提供统一的工具和对外出口。Configurations 不进入项目内部实现，也不替项目决定必须先构建、再打包、再链接等顺序；它只保证被使用的通用动作具备相应的记录、验证和反操作能力。

配置流程的结果由各配置流程自己产生和报告。Configurations 不替配置项目统筹依赖、顺序、失败策略或整体正确性。

Configurations 的模块职责包括：

- 决定并登记可提供的配置对象；
- 暴露各配置的应用与撤销能力；
- 接收编排者传入的环境变量、平台能力和平台差异数据；
- 提供配置流程需要的运行上下文、状态、所有权、备份和反操作支持。

以下职责属于外部编排者（通常是 Bootstrap）：

- 根据 Profile 选择配置；
- 决定 Packages 和 Configurations 阶段内部对象的顺序；
- 启动各配置的应用或撤销操作；
- 处理整体失败策略并汇总结果。

具体配置流程的内部步骤仍由配置项目自己拥有。

Configurations 不负责软件安装，也不负责环境变量的持久发布。

## Bootstrap

Bootstrap 负责：

- 读取声明和选择 Profile；
- 按固定的 Packages → Environment → Configurations 阶段顺序执行；
- 向后续模块传递必要的声明结果或运行时环境；
- 执行严格停止策略；
- 汇总成功、失败、未执行和残留。

Bootstrap 不负责包管理器命令、环境变量写入、文件链接、配置内容生成或模块内部回退。
